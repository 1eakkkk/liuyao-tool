# 局部依据：盘面事实、问题解释与现实建议

2026-10-03。候选 `packet-led-local-offline-1` 针对[前一轮真实失败](PACKET_LED_REVIEW.md)作有限离线补正；正式网站仍使用稳定版本。本阶段不调用 API，使用已曝光的第一个相册开发盘及手工文字，不用第二个未调用问题或受保护 holdout 调试。

## 完成的开发

沿用单选主次，每项因素选一至两个程序包，再选一至四个包内具体 `basis_ids`。程序只展示选中的事实、选中规则的严格来源闭包，以及该规则实际参与者的六亲身份背景。模型不用手填事实值，也不用重复列规则全部来源。整盘中存在的值不能跨段借作本段依据；本爻、变爻、伏神身份分开。包内局部 ID 增加了选择负担，因此保留小上限；后续真实测试还需检查模型是否能稳定使用，不能据离线结果认定已解决漏引。

选规则会自动展开原 `source_facts`，并标记哪些是规则前提。参与者六亲仅补充身份背景，不变成计算前提。未选的月令等状态不随整份身份包铺开。相同事实去重，不按条数计算趋势；相反因素不自动生成“利弊并存”。有明确方向时，主要因素的局部六亲事实或所选关系必须实际覆盖取用，不能只借一个未贡献局部依据的包。

展示分为三个区域：

- **程序依据**：程序生成原值、部件、关系与来源，默认收起；与假设和限制一起展开。
- **问题对应解释**：模型说明这些依据为何可能影响本次目标，用 `question_relevance` 代替属性复述；取象假设和限制单列。
- **现实建议**：独立展示一般操作建议，不被程序加入支持因素或规则来源。

直接回答和取舍仍是模型文字。无法建立相关性时可以选择 `unclear` 并不填因素。所有视图保留 `semantic_acceptance: unassessed` 与 `forecast_accuracy: unassessed`；程序没有能力从字段拆分证明解释正确。

## 验证边界与反例

14 项测试及独立工程复验通过，覆盖四类对照：

1. 第3爻与世应包不能覆盖第4爻的六亲；加入第四爻角色的局部依据后，事实覆盖成立，但“所以整理容易”仍未获证明。
2. 变爻／伏神包不能替代本爻父母水和飞伏关系；补选相应关系后，只证明程序关系及来源能正确展示。
3. 严格规则前提与六亲身份背景分开；其他爻“世爻否／应爻否”不构成取用覆盖。
4. 一般建议与卦盘判断分开；“必须每天筛选，否则一定无法成册”仍是未经证明的必要条件，不能因写在建议字段就认定安全。

另覆盖未知／重复／超量／稀疏引用、未知字段、克隆／跨 context、旧 schema 隔离、文本注入、无嵌套展开，以及校验失败时保持原展示。第一次局部测试暴露展示层使用了不存在的 `sourceIds` 属性，已改为读取真实规则的 `entry.source_facts`，重跑通过，没有修改原规则来源。

特别保留一个机械通过、语义应拒绝的手工反例：只选第3爻事实，却写“第4爻官鬼金旺，所以一定能够迅速成册”，并要求必须每天筛选。程序能验证 ID 归属、值与闭包，但不能自动解析并证实自由文字的属性、取象、权重或现实因果。下一轮真实内容检查仍必须逐段核对；不添加词语黑名单来制造“内容已通过”的假象。

## 归档与收尾

独立报告、手工样例及展示检查保存在 [本阶段归档](acceptance/packet-local-20261003/demo-plan.json)。这不是模型回答、盲测、预测成绩或正式网页真机验收。旧失败回复、付费计划、旧协议和旧账本均保留。

整体回归 **64 个测试文件／896 项通过**；正式发布边界仍是原 5 个资产。独立展示检查在 1280／390／320 像素、收起／展开共六种状态无横向溢出、无嵌套 details、无页面错误，采用已安装 Edge 的 Playwright 预览，不是 iPhone 真机。独立报告的 9 条 JSON Pointer／字段 UTF-16 引文经主代理再次核对，切片及手工样本数量均一致。

三份手工样例的结果分别是：有限拆分展示（不认证取法）、缺失局部依据被拒绝、自由文字反例机械通过但内容失败。后者在事实覆盖、论证支撑、建议边界和方向一致性均失败；没有把这个失败计为内容通过。本阶段 API 调用 **0 次、费用 0 元**，没有部署。

下一步在本阶段工程与展示验收完成后，另行冻结少量新的开发问题，检查模型能否使用局部引用，以及解释与当前目标之间有没有合理依据。知识库准入仍以具体取法的适用条件和出处核对为先；本阶段不以扩大古籍数量替代这项检查。真实内容达标后再考虑接入 API 与提示词导出并部署。
